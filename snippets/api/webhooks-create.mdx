
Crea un nuevo webhook para recibir notificaciones automáticas cuando ocurren eventos relacionados con documentos. El webhook se asocia con una entidad específica del usuario autenticado.

## ¿Para qué se usa?

Crea un nuevo webhook para recibir notificaciones automáticas cuando ocurren eventos relacionados con documentos. Útil para:
- Configurar notificaciones automáticas cuando se emiten documentos
- Recibir alertas cuando documentos son aceptados o rechazados por el SII
- Integrar con sistemas externos para procesamiento automático de documentos
- Monitorear el estado de entrega de documentos importantes

## Qué hace

- Crea un nuevo webhook asociado a una entidad específica
- Configura la URL de callback que recibirá las notificaciones
- Define los eventos específicos que se notificarán (emitido, entregado, rechazado, pagado, cancelado)
- Permite configurar una clave secreta para verificar la autenticidad de las notificaciones
- Establece el estado inicial del webhook (activo o inactivo)

## Ejemplos de uso

- **Notificaciones de emisión:** Configurar un webhook para recibir notificaciones cada vez que se emite un documento
- **Integración con ERP:** Conectar el sistema con un ERP externo para procesar documentos automáticamente
- **Alertas de rechazo:** Recibir notificaciones inmediatas cuando el SII rechaza un documento

## Consideraciones Importantes

### Entidad maestra
Debes especificar el `master_entity_id` de la entidad para la cual quieres crear el webhook. El usuario debe tener acceso a la entidad especificada.

### Ambiente (`environment`)
`both` (default) recibe los documentos de producción y de sandbox; `production` o `sandbox` los separan sobre la misma empresa. Los eventos que no son de documento (credenciales, folios, cobros, programados) se entregan como producción.

### Formato de identificadores (`api_version`)
`2`: todos los ids del payload son públicos (`docu_…`, `ment_…`), igual que la API v2. `1`: ids enteros, el contrato de la API v1. Si lo omites, el default sigue la ruta: `/v2/webhooks/` crea en 2 y `/v1/webhooks/` crea en 1. Ver [Identificadores en el payload](/user-guide/webhooks#identificadores-en-el-payload).

### Validación de URL
No puede existir un webhook con la misma URL para la misma entidad. Si intentas crear un webhook duplicado, recibirás un error de validación.

### Eventos disponibles
- `document.issued` - Documento emitido exitosamente
- `document.issue_failed` - Falló la emisión de un documento; trae el bloque `error` con su código
- `document.delivered` - Documento entregado al receptor
- `document.rejected` - Documento rechazado por el SII
- `document.paid` - Documento pagado
- `folio_request.completed` - Timbraje listo: el CAF se puede retirar
- `folio_request.failed` - El SII no autorizó folios; no se consumió nada
- `folio_request.authorized_without_caf` - El SII autorizó un rango y no entregó el archivo
- `document.unpaid` - Documento revertido de pagado a no pagado
- `document.cancelled` - Documento cancelado
- `batch.intake_failed` - Un lote de emisión masiva, o alguno de sus documentos, fue rechazado en la validación, antes de crear el documento
- `connection.active` / `connection.requires_action` - Estado de una conexión de Tupana Connect
- `bank_account.refreshed` - Una corrida de sync leyó la cuenta bancaria (saldo nuevo)
- `movement.created` - Esa corrida trajo movimientos nuevos (lista de ids, uno por cuenta y corrida)
- `bank_account.refresh_failed` - La lectura de la cuenta falló
- `connection.degraded` - Una cuenta quedó detenida tras fallos repetidos
- `card_movement.created` / `card_movement.billed` / `card_movement.updated` / `card_movement.removed` / `card_movement.reversed` - Cambios en movimientos de tarjeta de crédito
- `card_statement.mismatch` - Un estado de cuenta de tarjeta no cuadró

Los eventos bancarios se detallan en [Webhooks bancarios](/api-reference/v2/banking/webhooks). El payload de cada evento está en la [guía de webhooks](/user-guide/webhooks#payloads-por-evento).

### Errores que pueden llegar en un evento

**`document.issue_failed`** trae en `data.error` el campo `catalog_code`, un código estable contra el que puedes programar, junto con `retryable`, `suggested_action`, `user_message` y `doc_url`. Estos son sus valores posibles:

| `catalog_code` | Qué significa | ¿Reenviar? |
|----------------|---------------|:----------:|
| [`sii_unavailable`](/api-reference/errors/sii_unavailable) | El SII no estuvo disponible | Sí |
| [`sii_session_expired`](/api-reference/errors/sii_session_expired) | La sesión del SII venció | Sí |
| [`service_unavailable`](/api-reference/errors/service_unavailable) | Nuestro servicio no estuvo disponible por un momento | Sí |
| [`internal_error`](/api-reference/errors/internal_error) | Error interno de Tupana | Sí |
| [`sii_rejected`](/api-reference/errors/sii_rejected) | El SII rechazó el documento por sus datos | No, corrige lo que indica `message` |
| [`sii_unauthorized`](/api-reference/errors/sii_unauthorized) | La empresa no está autorizada en el SII para emitir | No, revisa la habilitación en el SII |
| [`no_active_credentials`](/api-reference/errors/no_active_credentials) | La empresa no tiene credenciales activas | No, reconecta la empresa |
| [`unprocessable`](/api-reference/errors/unprocessable) | Los datos del documento no se pueden procesar | No, ajusta los datos |
| [`conflict`](/api-reference/errors/conflict) | El documento choca con uno que ya existe | No, consulta el estado actual |

Para decidir si reenviar usa el `retryable` del evento, y deja un caso por defecto: `catalog_code` puede venir en `null`. Más detalle en [`document.issue_failed`](/user-guide/webhooks#documentissue_failed).

**`batch.intake_failed`** no trae códigos. Cada documento rechazado viene en `data.rejected_documents` con `errors`, el error de validación por campo con la misma forma que un `400` de la API. Para esos documentos no llega ningún evento `document.*`: corrígelos y envíalos en un lote nuevo. Más detalle en [`batch.intake_failed`](/user-guide/webhooks#batchintake_failed).
