En sandbox una emisión normal siempre termina bien. Para saber qué hace tu
integración cuando el SII rechaza un documento o no responde, emite en
sandbox a uno de estos **RUT de receptor de prueba**: el documento falla
igual que fallaría con el SII, y recorre el mismo camino que en producción.

## Los RUT de prueba

| RUT del receptor | Qué simula | Qué vas a ver |
| --- | --- | --- |
| `500.000.001-0` | El SII falla una vez y después responde | El primer intento falla y Tupana reintenta solo. El segundo emite y llega `document.issued` con folio `SANDBOX-…` |
| `500.000.002-9` | El SII no responde | Se agotan los reintentos automáticos y llega `document.issue_failed` con `sii_unavailable` |
| `500.000.003-7` | El SII rechaza el documento por sus datos | Fallo definitivo, sin reintentos: `document.issue_failed` con `sii_rejected` |
| `500.000.004-5` | La empresa no está autorizada a emitir | Fallo definitivo: `document.issue_failed` con `sii_unauthorized` |
| `500.000.005-3` | No quedan folios | Fallo definitivo: `document.issue_failed` |

Cualquier otro receptor emite como siempre.

## Cómo usarlos

Usa una **API key de sandbox** y envía el documento con el RUT de prueba en
`document_receiver.rut`. Nada más cambia en la llamada:

```bash
curl -X POST "https://api.tupana.ai/v2/documents/batch/" \
  -H "Authorization: Api-Key TU_API_KEY_DE_SANDBOX" \
  -H "Content-Type: application/json" \
  -H "X-Use-Defaults: true" \
  -d '{
    "documents": [{
      "dte_type": { "code": "33" },
      "document_issuer": { "rut": "RUT_DE_TU_EMPRESA_DE_PRUEBA" },
      "document_receiver": {
        "rut": "500.000.002-9",
        "business_name": "Receptor de prueba",
        "business_activity": "Servicios",
        "address": "Calle Falsa 123",
        "district": "Providencia",
        "city": "Santiago"
      },
      "details": [{ "item_name": "Prueba", "quantity": 1, "unit_price": 1000 }]
    }]
  }'
```

La llamada responde `201` igual que cualquier emisión: el resultado llega
después. El ciclo completo, con reintentos, toma menos de un minuto.

## Cómo te enteras del resultado

Igual que en producción:

- **Por webhook**: `document.issue_failed` trae el bloque `error` con el
  código (`catalog_code`), qué hacer (`suggested_action`), si conviene enviar
  el documento de nuevo (`retryable`) y el enlace a la página del código
  (`doc_url`). Ver [Webhooks](/guias/webhooks).
- **Sin webhook**: consulta
  [`GET /v2/events/?type=document.issue_failed`](/api-reference/v2/events/list#emisiones-que-fallaron).
- **En la consola**: Requests muestra cada llamada, y la tarjeta "Listo para
  producción" marca el paso de haber probado un error.

## Qué conviene probar

1. **No reintentes por tu cuenta un error que Tupana ya reintenta.** Con
   `500.000.001-0` el documento termina emitido sin que hagas nada: si tu
   sistema lo reenvía al primer fallo, emite dos veces.
2. **Decide qué haces cuando el fallo es definitivo.** Con `500.000.003-7` o
   `500.000.004-5` reenviar el mismo documento no sirve: hay que corregir el
   dato o la autorización.
3. **Usa una `Idempotency-Key`** en cada envío, para que un reintento de tu
   lado nunca cree un documento repetido.

## Lo que hay que saber

- **Solo existen en sandbox.** Con una API key de producción estos RUT se
  rechazan como inválidos antes de crear nada.
- **Un fallo por emisor afecta a la empresa de prueba entera**, igual que en
  producción: con `500.000.004-5`, los demás documentos pendientes de esa
  empresa también quedan en error. Envía ese caso por separado.
- No consumen folios ni llegan al SII.
